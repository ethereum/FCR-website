Faster confirmations for Ethereum users.

FCR can confirm L1 blocks in about 12–24 seconds. At 24 seconds versus a 780-second baseline, that is approximately 97% less waiting (32.5× faster). This is an illustrative comparison, not a latency guarantee.

FCR relies on counting attestations with safety guarantees under specific network and stake assumptions. A fixed block count alone does not provide the same guarantee.

No hard fork required. FCR is a consensus client feature. Check support and configuration in your chosen client or RPC provider before using its safe block tag.

Assumptions

FCR depends on network synchrony and bounds on adversarial stake in sampled committees. If confirmations stop advancing, wait or use a finality policy. Assumption violations are not always detectable; a fast-confirmed block can reorg if safety assumptions fail.

ASSUMPTION 01

Communication model (synchrony)

FCR requires attestations to be received by all honest validators by the end of the slot in which they are sent.

ASSUMPTION 02

Stake and committee sampling

Safety depends on the adversarial weight in relevant committees. A total-stake shortcut requires care with consolidated validators. The guide’s sampling explanation is awaiting technical review; consult the formal paper for precise assumptions.

Frequently asked

The Fast Confirmation Rule is built on rigorous research, but using it is simple. Below are answers to common questions. For anything else, reach out to fastconfirm@ethereum.org.

Why 24 seconds instead of the earlier single-slot / ~13-second message?+
Earlier messaging emphasized the single-slot best case. This page uses 24 seconds as an illustrative headline alongside the guide’s 12–24-second range. Julian’s proposal considered post-Glamsterdam timing; that forward-looking rationale needs technical confirmation and is not a claim that the upgrade is live. Actual latency depends on the protocol version, client, attestations and network conditions.
How much faster is FCR? +
The production guide describes about 12–24 seconds under favorable conditions. At 24 seconds against a roughly 13-minute (780-second) baseline, confirmation takes 32.5 times faster: about a 97% latency reduction. Confirmation can take longer or stall; this is not faster finality.
Does FCR require a hard fork? +
No. FCR is a client-side feature implemented in consensus clients. No protocol change, no devnet, and no hard fork are required. Nodes run the rule locally.
Is FCR as secure as finality? +
FCR and finality provide different guarantees. FCR relies on network synchrony and the stake and committee assumptions in its proof. Finality’s accountable safety tolerates asynchrony: conflicting finalization requires at least one-third of stake to violate slashable rules. FCR is complementary to finality. See the guide’s reorg scenarios before choosing a policy.
What happens if network conditions are poor? +
In most of the scenarios, FCR would just stall and eventually revert to finality. In some extreme circumstances, this could lead to a Fast Confirmed block being reorged.
Can an adversary delay my confirmation? +
Yes. Withheld attestations and degraded network conditions can delay or stall fast confirmation. The delay depends on adversarial participation and the rule’s configuration. Do not treat 24 seconds as a guaranteed upper bound.
Does FCR affect L2 security? +
Using FCR changes when an L2 accepts an L1 confirmation signal. The L2 must explicitly accept FCR’s assumptions and handle L1 reorgs and stalled confirmations. FCR does not remove other rollup or bridge risks.
What are slots and epochs? +
With 12-second slots, an epoch contains 32 slots (6.4 minutes). Finality proceeds through epoch checkpoints. The guide’s 12–24-second FCR estimate describes fast confirmation under favorable conditions, not a change to slot duration or finality.
How do I adopt FCR? +
Read the production guide, verify client/provider support and safe-tag semantics, and compare independent implementations. Define freshness, disagreement, value limits and finality fallback policies before enabling production flows.
What does the API return if something goes wrong? +
An FCR-backed safe head may stop advancing when fast confirmation stalls. Check freshness and provider health as well as the returned block hash. Implement an explicit wait or finality policy; an RPC response alone is not proof that FCR’s assumptions still hold.
Which clients support FCR? +
Support and flags vary by client release and RPC provider. Verify the implementation and configuration with your operator. The specification discussion is a starting point, not a guarantee that your provider has enabled FCR.
