Fast and Secure confirmations for users.

FCR reduces L1 to L2 or L1 to exchange deposit and message speed to about 13 seconds. That is 98.75% faster than finality.

FCR relies on counting attestations and is proven to be safe under normal network conditions. Waiting for a number of blocks is not.

Security first. If confidence drops below threshold, FCR automatically falls back to finality.

Trade-offs

FCR optimizes for speed; finality optimizes for extreme robustness.

Frequently asked

The Fast Confirmation Rule provides secure confirmations within 13 seconds. Although the exact algorithm is complex, the core idea relies on counting attestations. Using FCR is very easy! Feel free to get in touch by emailing fastconfirm@ethereum.org

What is the Fast Confirmation Rule (FCR)? +
FCR is an algorithm that provides near-instant transaction confirmations by analyzing validator attestation voting power in real-time. It determines that a block is secure based on deterministic logic, not probability; based on the weight of LMD-GHOST support it has gathered from the validator committee, if a transaction is fast confirmed, it is guaranteed to be finalized provided that standard network synchrony and adversarial threshold assumptions hold. Effectively, a fast-confirmed transaction will be finalized unless the network experiences exceptional circumstances.
Is a hard fork required to implement FCR? +
No. FCR is an out-of-protocol, opt-in upgrade for consensus clients. It requires no changes to the base Ethereum consensus layer, no hard fork, and no network-wide coordination; node operators can operate it independently.
Is FCR as secure as finality? +
FCR operates on a different security assumption than Casper FFG finality. While finality requires a 33% adversarial threshold and works under partial network synchrony, FCR assumes a 25% adversarial threshold and requires network synchrony. It is a complementary tool meant for speed, while FFG finalization remains the ultimate economic security guarantee.
What happens if network conditions are poor? +
The rule is designed with an automatic fallback mechanism. If support indicators (Q and P) fall below the required safety thresholds—due to high latency, missed slots, or low validator participation—the system simply reverts to standard protocol finality timing without compromising safety.
How much faster is FCR than the current system? +
FCR reduces confirmation times from the current 12–16 minutes (64 blocks) to approximately 13 seconds. This represents a 98.75% improvement in confirmation latency.
Which clients support FCR? +
Standardized specifications are being integrated into the Ethereum consensus specs (PR #4747). Support is actively being developed and implemented in major consensus clients, including Lighthouse, Prysm, and Teku.
Does FCR affect rollup and L2 security? +
L2s that use FCR will never finalize an invalid block. The worst case is that the L2 would need to reorg with the L1 in the exceptional case there is an adversary with more than 25% stake.
Can an adversary intentionally delay my confirmation? +
FCR is designed to be robust against manipulation. While adversaries may attempt to influence timing, successfully preventing or reverting a fast confirmation would require controlling a significant portion of the validator set (exceeding the 25% adversarial threshold). As long as the network remains below this threshold, FCR remains secure.
